## Цель

Зафиксировать фактическое состояние тестирования перед выполнением этапа 15. Новые тесты добавляются только для непокрытых сценариев; существующие проверки не дублируются.

## Текущее состояние

В проекте обнаружен 51 C#-файл в `Messenger.Tests`, включая тестовые классы, фикстуры и test doubles. Тестовый проект использует xUnit, Moq, ASP.NET Core TestHost, Testcontainers для PostgreSQL и Redis. Таргет — .NET 10.

### 15.1 Unit-тесты Application

**Частично выполнено.**

- `BroadcastServiceTests`: 5 тестов.
- `FileValidationServiceTests`: 9 тестов.
- В Application также есть небольшая утилита `UtcDateTime`; отдельного набора тестов для неё не обнаружено.
- Остальная часть Application в основном состоит из DTO, интерфейсов и сообщений, которым отдельные unit-тесты обычно не нужны.

Действие: проверить граничные случаи и поведение двух конкретных сервисов; не создавать искусственные тесты для DTO и интерфейсов.

### 15.2 Unit-тесты Infrastructure

**Широкое, но неравномерное покрытие.**

Есть отдельные наборы для пользователей, чатов, сообщений, аутентификации, настроек, вложений, уведомлений, push, модерации, расписания, Redis, файлового хранилища и безопасности. Часть тестов Infrastructure фактически является интеграционной: сервисы проверяются на реальном PostgreSQL через Testcontainers.

Примеры уже покрытых важных сценариев: проверка прав доступа, идемпотентность повторных операций, конкурентная регистрация пользователя, защита от регрессии статуса доставки, безопасное владение сессиями.

Действие: составить матрицу публичных методов сервисов и тестов, затем добавлять только критичные отсутствующие сценарии. Не смешивать unit- и integration-тесты в описании результатов.

### 15.3 Интеграционные тесты PostgreSQL

**Частично выполнено.**

- Общая PostgreSQL-фикстура использует Testcontainers и `EnsureCreatedAsync`.
- Отдельная миграционная фикстура проверяет применение полной цепочки миграций, отсутствие расхождений со snapshot и наличие ключевых таблиц.
- Есть проверки поведения внешних ключей и сервисов на PostgreSQL.

Пробел: `EnsureCreated` обходит миграции, поэтому обычные сервисные integration-тесты не проверяют реальный путь обновления схемы. Миграционный сценарий уже выделен отдельно — расширять его следует только при наличии конкретного риска.

### 15.4 Интеграционные тесты Redis

**Частично выполнено.**

Есть реальные Redis Testcontainers-тесты для кэша, fixed-window rate limiting, распределённой блокировки, presence, heartbeat, конкурентных подключений, истечения lease, восстановления после недоступности Redis и локального fallback.

Действие: проверить недостающие граничные сценарии и устойчивость тестов к гонкам/таймингам; существующие сценарии не дублировать.

### 15.5 API Contract Tests

**Покрытие ограничено.**

Есть HTTP integration-тесты middleware rate limiting на TestServer. Полноценного набора контрактных проверок контроллеров и HTTP API в дереве тестов не обнаружено.

Действие: добавить проверки наиболее важных API-контрактов: маршруты и коды ответа, DTO/JSON, валидация входных данных, авторизация и формат ошибок. Начать с нескольких репрезентативных контроллеров и общей инфраструктуры тестового хоста.

### 15.6 SignalR Tests

**Покрытие ограничено.**

Есть unit-тест ChatHub на запрет входа в группу для пользователя, который не является участником чата. Есть тесты фоновых компонентов, использующих SignalR hub context, но полноценного SignalR integration-теста соединения и вызова hub-методов не обнаружено.

Действие: добавить интеграционные сценарии авторизации подключения и доступа к группам/методам; отдельно проверить отключение и обработку отмены.

### 15.7 RabbitMQ Tests

**Не обнаружены.**

Есть unit-тест `ChatMessageSentConsumer`, проверяющий поведение при ошибке push-доставки и повторную обработку брокером. Это не проверяет реальный транспорт RabbitMQ, конфигурацию endpoint, сериализацию сообщения и retry/dead-letter поведение.

Действие: добавить ограниченный набор интеграционных тестов с RabbitMQ Testcontainers, если используемая конфигурация MassTransit допускает изолированный запуск брокера в тестах.

### 15.8 Concurrency Tests

**Частично выполнено.**

Уже проверяются конкурентная регистрация пользователя, идемпотентная отправка/создание вложений, конкурентная диспетчеризация запланированных сообщений, Redis distributed lock и переходы presence при параллельных подключениях/отключениях.

Действие: сопоставить конкурентно-чувствительные операции с существующими тестами и добавить проверки только для непокрытых операций. Приоритет — уникальность, идемпотентность, потерянные обновления и отсутствие двойной обработки.

### 15.9 Coverage Audit

**Не обнаружена автоматизированная инфраструктура отчёта покрытия.**

В тестовом проекте не обнаружена явная настройка Coverlet или отдельный сценарий генерации/публикации отчёта покрытия.

Действие: подключить сбор покрытия и зафиксировать воспроизводимую команду получения отчёта. Процент покрытия использовать как диагностическую метрику, а не как самостоятельную цель.

## Ограничения аудита

Это аудит структуры репозитория и прочитанного исходного кода тестов на указанном commit. Он не является отчётом о фактическом запуске тестов или измерении покрытия. Запуск .NET и Docker/Testcontainers должен быть подтверждён локально или CI.
