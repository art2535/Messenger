# File Storage и безопасность вложений

Дата: 2026-11-28  
Ветка: refactor/architecture

## Согласованный объём

В этап входят:
- порт `IFileStorage`;
- локальная реализация;
- проверка имени, размера, расширения и сигнатуры содержимого;
- единый безопасный процесс загрузки;
- очистка осиротевших файлов.

Не входят по решению пользователя:
- S3 / MinIO;
- антивирусный сервис;
- временные/signed URLs.

## Архитектура

| Компонент | Ответственность |
|---|---|
| Messenger.Application.Files.IFileStorage | Контракт файловых операций |
| FileStorageArea | Разделение областей Uploads и Avatars |
| StoredFileInfo | Имя, размер и время изменения файла |
| IFileValidationService | Контракт проверки загружаемого файла |
| FileValidationService | Проверка имени, размера, расширения и magic bytes |
| Messenger.Infrastructure.Files.LocalFileStorage | Локальная запись, чтение, удаление и перечисление |
| UploadOrphanCleanupService | Фоновая очистка старых файлов без ссылок |
| Messenger.API.Files.StoredFileNameGenerator | Генерация owner-prefixed имён и проверка владельца файла |

API регистрирует LocalFileStorage с корнем `{ContentRootPath}/wwwroot`. Файлы разделяются по каталогам:
- `wwwroot/uploads` — вложения сообщений;
- `wwwroot/avatars` — аватары.

Общий static-file provider не публикует uploads: отдельный middleware раздаёт только avatars. Имена новых вложений генерируются общим StoredFileNameGenerator на основе ID владельца, случайного GUID и проверенного расширения. Он используется для обычных сообщений, запланированных сообщений и копий вложений при пересылке. Клиентское имя сохраняется только как отображаемое имя. LocalFileStorage дополнительно отклоняет traversal, управляющие символы и имена длиннее 255 символов.

## Валидация

MIME определяется сервером по расширению и сигнатуре содержимого. Значение Content-Type от клиента не считается доверенным.

Поддерживаются:
- изображения: JPG, JPEG, PNG, GIF, WEBP, BMP, AVIF;
- документы: PDF, TXT, CSV, DOC, XLS, PPT, DOCX, XLSX, PPTX;
- архивы: ZIP;
- медиа: MP3, MP4, WAV.

Ограничения:

| Сценарий | Ограничение |
|---|---:|
| Один файл-вложение | 10 МБ |
| Вложения одного сообщения | 20 файлов |
| Суммарный размер вложений | 50 МБ |
| Аватар | 2 МБ |
| Multipart body сообщений/запланированных сообщений | 60 МБ |
| Multipart body аватара | 3 МБ |

Пустые файлы, неизвестные расширения, некорректные имена и несовпадение сигнатуры с расширением отклоняются. Лимит размера дополнительно проверяется во время фактического копирования потока в хранилище.

## Потоки загрузки и выдачи

### Сообщения и пересылка

MessagesController проверяет членство пользователя в чате, ограничения количества и размера, валидирует каждый файл и сохраняет его через IFileStorage. При неудаче до публикации сообщения новые файлы удаляются.

При пересылке исходный файл повторно проверяется по содержимому, копируется под новым серверным именем, а MIME определяется заново.

Новые файлы вложений получают owner prefix `{userId:N}_`. Это позволяет legacy metadata endpoint `POST /attachments/{messageId}` проверить владельца файла и не дать прикрепить к своему сообщению файл другого пользователя, даже если его URL или имя стало известно. Старые файлы без префикса продолжают скачиваться через существующие attachment records; новые metadata records для таких файлов не создаются.

### Запланированные сообщения

ScheduledMessagesController использует тот же validator и storage port. При ошибке создания запланированного сообщения сохранённые в рамках запроса файлы очищаются.

### Аватары

UserService проверяет, что файл является поддерживаемым растровым изображением, сохраняет его в области Avatars и обновляет ссылку в БД. Новый файл удаляется при ошибке загрузки/сохранения БД. Старый файл не удаляется немедленно: он становится orphan и удаляется общей фоновой очисткой после grace period, чтобы не сломать возможные legacy-ссылки из других аккаунтов.

Аватары остаются публичными статическими файлами. Произвольная установка URL аватара через update-profile удалена: смена аватара выполняется через upload endpoint.

### Скачивание вложений

Вложения не раздаются как статические файлы. Web-клиент загружает их через защищённый API endpoint `/api/v1/attachments/file/{attachmentId}` с Bearer-токеном; старый публичный proxy `/uploads` удалён. AttachmentsController:
1. загружает метаданные вложения;
2. проверяет доступ к сообщению и членство в чате;
3. проверяет API origin и область uploads;
4. получает файл через IFileStorage;
5. повторно проверяет сигнатуру и MIME;
6. отдаёт inline только известные растровые изображения, остальные файлы — как attachment;
7. выставляет X-Content-Type-Options: nosniff.

Некорректные URL и percent-encoded пути отклоняются как недопустимые, а не превращаются в ошибку сервера.

## Очистка orphan-файлов

UploadOrphanCleanupService запускается каждые 6 часов. Файл рассматривается как кандидат на удаление, только если он старше 30 дней и на него нет ссылки. Это относится как к вложениям, так и к старым аватарам после замены или удаления.

Сервис сохраняет файлы, на которые ссылаются:
- строки таблицы вложений;
- аватары в настройках аккаунтов;
- pending scheduled messages (AttachmentsJson);
- transactional outbox события ChatMessageSent.

Удаление файлов после удаления сообщения намеренно отложено: это предотвращает удаление файла, который ещё используется другим вложением или находится в процессе доставки. Неизвестный/неразбираемый payload приводит к пропуску цикла очистки, а не к рискованному удалению.

## Структура тестов

Тесты файлов разнесены по слоям и более узким каталогам:
- `Messenger.Tests/Application/Files/Validation` — проверка форматов и ограничений;
- `Messenger.Tests/Infrastructure/Files/Local` — локальное хранилище;
- `Messenger.Tests/Api/Files/Cleanup` — очистка orphan-файлов;
- `Messenger.Tests/Api/Files/Upload` — генерация имён и ownership prefix.

Также разделены смешанные тестовые наборы:
- ChatService и MessageService;
- UserService и BroadcastRepository;
- AccountSettingsService и UserStatusService;
- ChatFolderService и ReactionService;
- отдельные классы для SessionCleanup, ScheduledMessageDispatcher, LogRetention, PresenceHeartbeat и Redis metrics.

Namespaces отражают структуру каталогов. Каждый тестовый класс находится в отдельном файле; fixtures и test doubles также разнесены по отдельным файлам в Shared.

## Ограничения

- Используется локальное хранилище на файловой системе API. Для нескольких API-реплик требуется общее persistent storage; S3/MinIO в этот этап не входят.
- Антивирусная проверка и временные ссылки не реализуются.
- Upload-контракт не выполняет распаковку архивов и не интерпретирует содержимое документов.
- В текущей среде отсутствует .NET SDK, поэтому dotnet build и dotnet test не запускались. Добавленные тесты должны быть выполнены в окружении проекта перед закрытием этапа.
