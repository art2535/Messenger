# Аудит сервисного слоя

## Назначение и правила ведения

Документ фиксирует аудит сервисного слоя всего решения, а не только классов из `Messenger.Infrastructure/Services`. В область проверки входят реализации, Application-контракты, фоновые службы, realtime-компоненты и инфраструктура токенов/кэша.

Аудит ведётся по фактическому коду ветки `refactor/architecture`. Статус «исправлено» означает, что соответствующее изменение уже присутствует в истории этой ветки. Статус «требует проверки» означает, что проблема обнаружена, но исправление ещё не внесено либо требует проверки вызывающих сторон и семантики.

Не считаются доказательством корректности: наличие CancellationToken только в интерфейсе, локальная проверка перед записью при наличии уникального ограничения, или успешное чтение/изменение файла на GitHub. Сборка и тесты должны быть выполнены отдельно.

## Проверенная ревизия

- Последнее обновление Presence и cleanup: коммит будет указан после публикации изменений.
- Основная область: `Messenger.Infrastructure/Services`, `Messenger.Application/Services`, `Messenger.Application/Interfaces`, `Messenger.API/Services`, `Messenger.Web/Services`, `Messenger.Realtime/Services`.
- Проверка локальной сборкой в этой среде недоступна: .NET SDK/runtime отсутствует.

## Presence и очистка неактивных сессий

`RedisUserPresenceTracker` хранит SignalR connection ID в Redis Sorted Set с lease 60 секунд. Heartbeat продлевает lease локальных подключений каждые 20 секунд. Добавлен `HasActiveConnectionsAsync`: проверка атомарно удаляет истёкшие lease и возвращает наличие действующих подключений. При отсутствии Redis используется локальный режим, допустимый только для одного экземпляра API.

`SessionCleanupBackgroundService` выбирает кандидатов по `LastActivity`, но теперь дополнительно проверяет фактические SignalR lease. Пользователи с активным подключением исключаются из перевода Offline и закрытия login-сессий. После пакетного перевода Offline выполняется повторная проверка Presence: если подключение появилось в промежутке, статус Online восстанавливается, а такой пользователь исключается из закрытия сессий и рассылки Offline.

При недоступности Redis проверка Presence завершится ошибкой, и текущий тик очистки будет пропущен. Это намеренная fail-safe семантика: нельзя переводить пользователей Offline, когда невозможно подтвердить отсутствие соединений. При Redis outage lease может истечь, поэтому после восстановления Redis heartbeat восстанавливает lease активных локальных подключений.

Ограничение: проверка Redis и запись в БД не образуют общей транзакции. Повторная проверка сужает гонку переподключения, но не обеспечивает строгую линейризуемость между Redis и PostgreSQL. Для строгой гарантии понадобится единый протокол координации переходов Presence и cleanup (например, распределённая блокировка на пользователя с одинаковым порядком захвата во всех путях).

Idle cleanup по-прежнему учитывает пользовательскую настройку `IdleLogout`: `CloseActiveLoginsForIdleUsersAsync` закрывает сессии только если настройка отсутствует или включена. Активные SignalR-подключения не затрагиваются.

## Открытые дефекты и следующие действия

### 1. Внешняя регистрация и уникальность ExternalId

Исправлено в миграции `20261127180000_AddUniqueExternalId` и сервисе `UserService`. Конфигурация и snapshot EF Core содержат уникальный фильтрованный индекс `IX_Users_External_ID`: NULL допускается, непустой идентификатор уникален. До нормализации миграция проверяет дубликаты после `btrim` и прерывается с перечнем конфликтующих значений; она не удаляет и не объединяет пользователей. Пустые и состоящие из пробелов значения нормализуются в NULL.

Регистрация отклоняет null/whitespace, обрезает пробелы по краям и ограничивает длину 255 символами. При нарушении именно индекса External_ID проигравшая конкурентная регистрация отсоединяет только свой добавленный граф и загружает уже созданного пользователя. Другие нарушения уникальности не маскируются. `GetUserByExternalIdAsync` теперь загружает роли вместе с пользователем.

Перед применением миграции на реальной БД необходимо выполнить backup и проверить её SQL на staging: если есть дубликаты, миграция намеренно остановится; их требуется разрешить вручную, сохранив связи и историю.
### 2. Планировщик сообщений: повторная публикация

Текущая последовательность «получить Pending → опубликовать → отметить Sent» не является атомарной. Параллельные диспетчеры могут опубликовать одно сообщение дважды; падение после публикации, но до отметки Sent, также приводит к повтору.

Нужен отдельный дизайн claim/lease или transactional outbox с идемпотентным ключом. Нельзя считать простую блокировку процесса достаточной для нескольких экземпляров приложения.

### 3. Остальные обязательные направления

- Проверить файловые операции `AttachmentService`: ограничения размера, имена и пути, очистка orphan-файлов, согласованность БД и файлового хранилища.
- Проверить `MessageService` и `ChatService`: права доступа, атомарность удаления/изменения, cache invalidation и поведение при частичном отказе.
- Проверить `ModerationService`: конкурентные mute/report-операции, проверку прав и аудит действий.
- Проверить `NotificationService` и `PushSubscriptionService`: идемпотентность, очистку недействительных endpoint и границы обработки ошибок.
- Проверить `RedisCacheService` и rate limiter: TTL, отмену, деградацию Redis и корректность ключей.
- Проверить фоновые службы: остановку приложения, retry/backoff, отсутствие бесконечных циклов и корректную обработку отмены.
- Проверить Application-контракты на полноту CancellationToken и отсутствие инфраструктурных типов.

## Критерии завершения аудита

- Каждый сервис и его интерфейс просмотрены вместе с основными вызывающими сторонами.
- Для каждой найденной проблемы есть исправление либо отдельная запись с обоснованием, почему изменение отложено.
- Проверены необходимые уникальные ограничения и индексы БД.
- Проверены конкурентные сценарии, отмена, ошибки внешних систем и файловые операции.
- Документация обновлена по фактическим результатам, а не по плану.
- Выполнены `dotnet build`, тесты и проверки миграций в окружении с .NET SDK и PostgreSQL; до этого сборка не считается подтверждённой.
