# Аудит сервисного слоя

## Назначение и правила ведения

Документ фиксирует аудит сервисного слоя всего решения, а не только классов из `Messenger.Infrastructure/Services`. В область проверки входят реализации, Application-контракты, фоновые службы, realtime-компоненты и инфраструктура токенов/кэша.

Аудит ведётся по фактическому коду ветки `refactor/architecture`. Статус «исправлено» означает, что соответствующее изменение уже присутствует в истории этой ветки. Статус «требует проверки» означает, что проблема обнаружена, но исправление ещё не внесено либо требует проверки вызывающих сторон и семантики.

Не считаются доказательством корректности: наличие CancellationToken только в интерфейсе, локальная проверка перед записью при наличии уникального ограничения, или успешное чтение/изменение файла на GitHub. Сборка и тесты должны быть выполнены отдельно.

## Открытые дефекты и следующие действия

### 1. LoginService: согласованность активных сессий и статуса пользователя

В `RevokeLoginAndUpdateStatusAsync` и `ExpireSessionAsync` выполняются отдельные чтения активных сессий и последующая запись статуса. Два параллельных завершения разных сессий одного пользователя могут оба увидеть ещё одну активную сессию и оба пропустить перевод пользователя Offline.

Кроме того, набор активных сессий меняют и другие методы: `AddLoginAsync`, `CloseLoginAsync`, `RevokeLoginAsync`, `RevokeOtherLoginsAsync`, `CloseActiveLoginsForUsersAsync`, `CloseActiveLoginsForIdleUsersAsync`. Нельзя исправить гонку только в двух методах: все конкурирующие операции должны использовать согласованный механизм сериализации.

Проверка `ChatHub` подтвердила, что `UserStatus.Online` фактически отражает SignalR presence: `OnConnectedAsync` выставляет Online=true, а `OnDisconnectedAsync` — Online=false. Поэтому `RevokeLoginAndUpdateStatusAsync` смешивает две разные модели состояния: отсутствие активных login-сессий не доказывает отсутствие SignalR-соединений. Нельзя просто сериализовать этот метод и считать проблему решённой.

Дополнительно `ChatHub.OnDisconnectedAsync` безусловно выставляет Offline при отключении каждого соединения. Если у пользователя открыто несколько вкладок/устройств, закрытие одного соединения может ошибочно показать Offline при оставшемся активном соединении. Для корректного исправления нужен учёт SignalR connections на пользователя (с учётом нескольких экземпляров API и выбранного backplane) и обновление статуса только при переходе количества соединений 0↔1. Также требуется проверить, где обновляется `LastActivity`: без регулярного обновления idle cleanup может ошибочно завершать активных пользователей. Распределённый tracker добавлен: `RedisUserPresenceTracker` хранит подключения в Redis Sorted Set с lease 60 секунд, атомарно определяет переходы 0↔1, а `PresenceHeartbeatBackgroundService` продлевает lease локальных подключений каждые 20 секунд. При отсутствии Redis действует локальный режим, допустимый только для одного экземпляра API. `ChatHub` использует tracker; `LoginService` больше не меняет `UserStatus.Online` при отзыве/истечении login-сессии. Требуется отдельная проверка cleanup-сценария и восстановления presence при Redis outage.

### 2. UserService: безопасная замена и удаление аватаров — исправлено

`UploadAvatarAsync` теперь проверяет размер (не более 2 МБ), расширение и сигнатуру содержимого изображения до записи. Новый файл получает уникальное имя и сохраняется отдельно; ссылка в БД обновляется только после успешной записи. При ошибке записи/сохранения выполняется попытка удалить новый файл, старый файл остаётся нетронутым. Старый файл удаляется только после успешного SaveChanges.

Разрешение старого файла ограничено каталогом `wwwroot/avatars`: для абсолютных URL дополнительно сверяется origin с настроенным URL API, а имя файла извлекается через `Path.GetFileName`. Внешние URL и пути вне каталога аватаров не удаляются.

`DeleteAvatarAsync` сначала сохраняет null в БД и только после этого пытается удалить файл. Ошибка очистки может оставить orphan-файл, но не битую ссылку в профиле. Компиляция и тесты этих изменений пока не подтверждены.

### 3. Внешняя регистрация и уникальность ExternalId

`RegisterExternalUserAsync` сначала ищет пользователя, затем добавляет нового. Проверка не защищает от двух одновременных регистраций одного внешнего идентификатора.

В текущем model snapshot на момент проверки не подтверждён уникальный индекс для `User.ExternalId`. Перед добавлением миграции необходимо:
- проверить существующие дубликаты;
- проверить семантику null и пустых ExternalId;
- согласовать фильтр уникального индекса, если null допустим;
- добавить миграцию и обработать UniqueViolation при конкурентной регистрации, повторно загрузив победившую запись.

### 4. Broadcast: отмена в Application-контрактах — исправлено

`IBroadcastService` и `IBroadcastRepository` принимают `CancellationToken` во всех операциях. `BroadcastService` передаёт token в репозиторий; `EfBroadcastRepository` передаёт его во все EF Core-запросы и `SaveChangesAsync`. `BroadcastsController` передаёт request token во все операции и пробрасывает отмену клиентского запроса вместо преобразования её в HTTP 500. Компиляция и поиск дополнительных потребителей контрактов ещё не выполнены.

### 5. Планировщик сообщений: повторная публикация

Текущая последовательность «получить Pending → опубликовать → отметить Sent» не является атомарной. Параллельные диспетчеры могут опубликовать одно сообщение дважды; падение после публикации, но до отметки Sent, также приводит к повтору.

Нужен отдельный дизайн claim/lease или transactional outbox с идемпотентным ключом. Нельзя считать простую блокировку процесса достаточной для нескольких экземпляров приложения.

### 6. Остальные обязательные направления

- Проверить файловые операции `AttachmentService`: ограничения размера, имена и пути, очистка orphan-файлов, согласованность БД и файлового хранилища.
- Проверить `MessageService` и `ChatService`: права доступа, атомарность удаления/изменения, cache invalidation и поведение при частичном отказе.
- Проверить `ModerationService`: конкурентные mute/report-операции, проверку прав и аудит действий.
- Проверить `NotificationService` и `PushSubscriptionService`: идемпотентность, очистку недействительных endpoint и границы обработки ошибок.
- Проверить `RedisCacheService` и rate limiter: TTL, отмену, деградацию Redis и корректность ключей.
- Проверить фоновые службы: остановку приложения, retry/backoff, отсутствие бесконечных циклов и корректную обработку отмены.
- Проверить Application-контракты на полноту CancellationToken и отсутствие инфраструктурных типов.

## Критерии завершения аудита

- Каждый сервис и его интерфейс просмотрены вместе с основными вызывающими сторонами.
- Для каждой найденной проблемы есть исправление либо отдельная запись с обоснованием, почему изменение отложено.
- Проверены необходимые уникальные ограничения и индексы БД.
- Проверены конкурентные сценарии, отмена, ошибки внешних систем и файловые операции.
- Документация обновлена по фактическим результатам, а не по плану.
- Выполнены `dotnet build`, тесты и проверки миграций в окружении с .NET SDK и PostgreSQL; до этого сборка не считается подтверждённой.
