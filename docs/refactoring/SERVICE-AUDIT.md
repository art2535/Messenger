# Аудит сервисного слоя

## Назначение и правила ведения

Документ фиксирует аудит сервисного слоя всего решения, а не только классов из `Messenger.Infrastructure/Services`. В область проверки входят реализации, Application-контракты, фоновые службы, realtime-компоненты и инфраструктура токенов/кэша.

Аудит ведётся по фактическому коду ветки `refactor/architecture`. Статус «исправлено» означает, что соответствующее изменение уже присутствует в истории этой ветки. Статус «требует проверки» означает, что проблема обнаружена, но исправление ещё не внесено либо требует проверки вызывающих сторон и семантики.

Не считаются доказательством корректности: наличие CancellationToken только в интерфейсе, локальная проверка перед записью при наличии уникального ограничения, или успешное чтение/изменение файла на GitHub. Сборка и тесты должны быть выполнены отдельно.

## Проверенная ревизия

- Последнее обновление аудита: проверены основные внутренние consumers/background/realtime callers, отмена доведена до ChatHub и Redis metrics; Program.cs разделён на API composition extensions. Предыдущие подэтапы API cancellation и Application contracts сохранены.
- Основная область: `Messenger.Infrastructure/Services`, `Messenger.Application/Services`, `Messenger.Application/Interfaces`, `Messenger.API/Services`, `Messenger.Web/Services`, `Messenger.Realtime/Services`.
- Проверка локальной сборкой в этой среде недоступна: .NET SDK/runtime отсутствует.

## Presence и очистка неактивных сессий

`RedisUserPresenceTracker` хранит SignalR connection ID в Redis Sorted Set с lease 60 секунд. Heartbeat продлевает lease локальных подключений каждые 20 секунд. Добавлен `HasActiveConnectionsAsync`: проверка атомарно удаляет истёкшие lease и возвращает наличие действующих подключений. При отсутствии Redis используется локальный режим, допустимый только для одного экземпляра API.

`SessionCleanupBackgroundService` выбирает кандидатов по `LastActivity`, но теперь дополнительно проверяет фактические SignalR lease. Пользователи с активным подключением исключаются из перевода Offline и закрытия login-сессий. После пакетного перевода Offline выполняется повторная проверка Presence: если подключение появилось в промежутке, статус Online восстанавливается, а такой пользователь исключается из закрытия сессий и рассылки Offline.

При недоступности Redis проверка Presence завершится ошибкой, и текущий тик очистки будет пропущен. Это намеренная fail-safe семантика: нельзя переводить пользователей Offline, когда невозможно подтвердить отсутствие соединений. При Redis outage lease может истечь, поэтому после восстановления Redis heartbeat восстанавливает lease активных локальных подключений.

Ограничение: проверка Redis и запись в БД не образуют общей транзакции. Повторная проверка сужает гонку переподключения, но не обеспечивает строгую линейризуемость между Redis и PostgreSQL. Для строгой гарантии понадобится единый протокол координации переходов Presence и cleanup (например, распределённая блокировка на пользователя с одинаковым порядком захвата во всех путях).

Idle cleanup по-прежнему учитывает пользовательскую настройку `IdleLogout`: `CloseActiveLoginsForIdleUsersAsync` закрывает сессии только если настройка отсутствует или включена. Активные SignalR-подключения не затрагиваются.

## Открытые дефекты и следующие действия

### 1. Внешняя регистрация и уникальность ExternalId

Исправлено в миграции `20261127180000_AddUniqueExternalId` и сервисе `UserService`. Конфигурация и snapshot EF Core содержат уникальный фильтрованный индекс `IX_Users_External_ID`: NULL допускается, непустой идентификатор уникален. До нормализации миграция проверяет дубликаты после `btrim` и прерывается с перечнем конфликтующих значений; она не удаляет и не объединяет пользователей. Пустые и состоящие из пробелов значения нормализуются в NULL.

Регистрация отклоняет null/whitespace, обрезает пробелы по краям и ограничивает длину 255 символами. При нарушении именно индекса External_ID проигравшая конкурентная регистрация отсоединяет только свой добавленный граф и загружает уже созданного пользователя. Другие нарушения уникальности не маскируются. `GetUserByExternalIdAsync` теперь загружает роли вместе с пользователем.

Перед применением миграции на реальной БД необходимо выполнить backup и проверить её SQL на staging: если есть дубликаты, миграция намеренно остановится; их требуется разрешить вручную, сохранив связи и историю.
### 2. Планировщик сообщений: атомарный захват и transactional outbox

Исправлено в текущей ветке. `ScheduledMessageDispatcherService` больше не использует единственную Redis-блокировку на весь планировщик и не выполняет раздельные операции «прочитать Pending → опубликовать → отметить Sent».

`ScheduledMessageService.DispatchDueAsync` выбирает по одной готовой записи через PostgreSQL `FOR UPDATE SKIP LOCKED` внутри транзакции. Разные экземпляры API не могут одновременно захватить одну строку: второй экземпляр пропускает уже заблокированную запись и выбирает следующую. В той же scoped-области `IPublishEndpoint` работает через уже настроенный MassTransit Entity Framework Bus Outbox (`UseBusOutbox`). Событие `ChatMessageSent` и переход `ScheduledMessage` в `Sent` сохраняются одним `SaveChanges` и фиксируются одним commit.

Падение до commit откатывает и изменение статуса, и outbox-запись; после commit событие остаётся в outbox и будет доставлено MassTransit независимо от перезапуска API. Это устраняет окно между публикацией в брокер и отметкой `Sent` на стороне планировщика. Доставка из outbox в RabbitMQ и обработка consumer остаются at-least-once; побочные эффекты consumer (SignalR/push) требуют отдельной идемпотентности и не становятся exactly-once автоматически.

Редактирование также переведено на условный SQL UPDATE с `Status = Pending`, поэтому конкурентное изменение не может перезаписать уже отправленную запись. Отмена уже использует такой же условный UPDATE. Новые поля и миграция не нужны: MassTransit outbox и его таблицы уже зарегистрированы в `GuapMessengerContext` и миграционной модели.

Нужно подтвердить интеграционными тестами на PostgreSQL два параллельных диспетчера, rollback между публикацией в Bus Outbox и commit, восстановление после рестарта и гонки редактирования/отмены.

### 3. Повторная доставка ChatMessageSent

Исправлена идемпотентность основных записей БД. `MessageService.AddMessageAsync` после блокировки чата проверяет `MessageId`: повторное событие с тем же чатом, отправителем, текстом и флагом вложений возвращает существующую запись без выделения нового SequenceNumber. Повторное использование того же MessageId с другим содержимым отклоняется. `AttachmentService` получил перегрузку с явным AttachmentId; consumer передаёт стабильный идентификатор из `AttachmentInfo`, а повторная вставка сверяет принадлежность и метаданные вложения. Конфликт с другим вложением не маскируется.

Переход статуса сделан условным: повторный сбой не может понизить Delivered/Read до Failed, а Delivered не перезаписывает Read. Это не обеспечивает exactly-once для внешних эффектов. Между отправкой SignalR/Push и подтверждением сообщения брокеру остаётся окно, в котором повторная доставка может повторить уведомление. Для строгой гарантии понадобится durable delivery outbox с отдельными записями на получателя и идемпотентный обработчик/клиент; внешние push-провайдеры не участвуют в транзакции PostgreSQL.

### 7. Проверки доступа к операциям чатов и сообщений

Авторизация перенесена из одной только HTTP-границы в сервисный слой:

- ChatService.AddParticipantToChatAsync, DeleteParticipantFromChatAsync, UpdateChatAsync и DeleteChatAsync принимают actorId, проверяют членство и роль инициатора внутри транзакции.
- Добавление допускает только обычную роль участника; удалить владельца/администратора и выполнить административное самоудаление нельзя. Удаление чата требует совпадения actorId с владельцем чата.
- Actor-aware read overloads GetChatByIdAsync и GetChatParticipantsAsync проверяют членство. HTTP-контроллеры используют защищённые overloads.
- MessageService повторно проверяет членство/авторство для чтения и мутаций; bulk delete проверяет весь набор до изменения.
- Инвалидация Redis после commit не должна превращать уже завершённую запись в ошибку запроса.

Дополнительная защита кешированного списка чатов: GetUserChatsWithLastMessageAsync теперь сверяет набор ChatId из Redis с актуальным составом ChatParticipants в PostgreSQL перед возвратом кеша. При расхождении кеш инвалидируется и список перестраивается из БД. Это закрывает утечку метаданных чата при неудачной best-effort инвалидации после удаления участника, а также обнаруживает пропущенные новые чаты. Создание чата использует best-effort инвалидацию аналогично другим мутациям.

Ограничение: проверка роли и изменение данных выполняются в одной транзакции, но PostgreSQL READ COMMITTED сам по себе не сериализует все параллельные операции изменения состава/ролей. Если появится отдельный сценарий смены ролей или удаления участников, он должен использовать тот же протокол блокировки строки чата; проверка в контроллере не заменяет этот протокол.

### 5. Идемпотентность уведомлений и повторная отправка Push

Для уведомлений, создаваемых при обработке `ChatMessageSent`, добавлено поле `Notifications.Deduplication_Key` с уникальным фильтрованным индексом PostgreSQL. Ключ формируется детерминированно из MessageId и UserId получателя. `NotificationService` сериализует создание одинакового ключа транзакционной advisory-блокировкой PostgreSQL: повторная доставка возвращает существующий NotificationId, не создавая вторую строку. Существующие уведомления сохраняют NULL в новом поле и не затрагиваются миграцией.

`PushSubscriptionService` передаёт этот ключ при обработке сообщения. Один и тот же NotificationId включается в повторные push payloads; service worker уже использует notificationId как основу notification tag и подавляет повторный показ существующего уведомления. SignalR-события сообщения уже содержат MessageId, который клиент может использовать как ключ дедупликации.

Ошибки отправки push и создания уведомления больше не подавляются внутри PushSubscriptionService и соответствующего участка ChatMessageSentConsumer: после логирования они пробрасываются MassTransit. В текущей конфигурации RabbitMQ задан `UseMessageRetry` с `Incremental(5, 2 секунды, 3 секунды)`, поэтому transient-сбой получает повторные попытки; после исчерпания retry сообщение переходит в штатный error flow MassTransit. Отмена также пробрасывается. Ошибки невалидных подписок, распознанные существующей проверкой WebPushException, по-прежнему приводят к удалению endpoint и не требуют повтора.

Ограничения: PostgreSQL и внешний Web Push provider не участвуют в общей транзакции. Если провайдер принял push, но consumer не успел подтвердить сообщение, повторная отправка возможна; одинаковый notificationId/tag подавляет повторный показ, пока уведомление с этим tag ещё отображается; service worker автоматически закрывает его через 4–8 секунд, поэтому поздний повтор может показать его снова. Это не гарантирует exactly-once на уровне ОС или провайдера. Уведомления, создаваемые без MessageId (например, прямым вызовом API), остаются без ключа идемпотентности. SignalR-доставка остаётся ephemeral и не защищена durable outbox. MassTransit Consumer Inbox этим изменением не включался.

Для полного подтверждения требуются интеграционные тесты на PostgreSQL: конкурентное создание одного deduplication key, повторная доставка после частичного push-сбоя, а также проверка уникального индекса и миграции.


### 6. Безопасность файловых вложений и очистка временных файлов

В `MessagesController` ограничена загрузка одного сообщения: не более 20 файлов, до 10 МБ каждый и до 50 МБ суммарно; multipart/request body ограничен 60 МБ. Пустые файлы отклоняются. Имя пользователя больше не используется как часть физического пути: на диске создаётся случайное имя с проверенным ASCII-расширением, а исходное имя нормализуется до basename, очищается от управляющих символов и ограничивается 255 символами. Файл создаётся через `FileMode.CreateNew`, без перезаписи существующего пути.

Для путей вложений добавлена канонизация через `Path.GetFullPath` и проверка нахождения внутри каталога `wwwroot/uploads`; при пересылке basename извлекается после нормализации разделителей и URL-декодирования. Копирование пересылаемых файлов также использует `CreateNew`-семантику (`overwrite: false`).

Если публикация `ChatMessageSent` не завершилась успешно, новые файлы исходящего сообщения или пересылки удаляются. Если очистка не удалась из-за IO/прав доступа, ошибка логируется, а orphan-файл остаётся видимым для последующей уборки. После успешной публикации файл не удаляется, даже если последующая SignalR-рассылка завершилась ошибкой.

Прямая публичная раздача `/uploads` удалена. Авторизованный endpoint выдачи вложений выставляет `X-Content-Type-Options: nosniff`; SVG и другие небезопасные типы принудительно скачиваются, а inline-выдача ограничена безопасными raster-форматами. MIME-тип из браузера остаётся недоверенной метаинформацией и не используется как основание для inline-рендеринга сервером.

Аватары сохраняют уже реализованные проверки размера и сигнатуры JPEG/PNG/GIF/WebP, случайные имена и порядок «записать файл → сохранить ссылку в БД → удалить старый файл». После успешного удаления сообщения его локальные файлы удаляются только при совпадении origin с настроенным API и пути `/uploads/`; ошибки удаления логируются и оставляют orphan-файл, не ломая уже завершённое удаление из БД. Single и bulk delete очищают файлы удалённых сообщений; оба пути проверяют авторство сообщения, а bulk delete дополнительно проверяет членство пользователя в чате. `AttachmentsController` проверяет членство в чате при чтении метаданных, а создавать метаданные может только автор сообщения — участник чата. POST дополнительно проверяет, что URL принадлежит настроенному API, ведёт к существующему файлу непосредственно в `/uploads/`, а фактический размер совпадает с заявленным. Добавлен `UploadOrphanCleanupService`: каждые 6 часов он сверяет файлы `uploads` и `avatars` со ссылками в `Attachments`, `AccountSettings` и сохраняющимися сообщениями transactional Bus Outbox; удаляются только неиспользуемые файлы старше 30 дней. Длительный grace period снижает риск удаления файла, пока опубликованное событие ещё ожидает обработки consumer. Если БД или конфигурация недоступны, очистка пропускается/повторяется позже; отдельные ошибки удаления не останавливают обработку остальных файлов. Публичная раздача `/uploads` удалена. Вложения выдаются через авторизованный endpoint `GET /api/v{version}/attachments/file/{attachmentId}`, который проверяет аутентифицированного пользователя, принадлежность вложения сообщению и членство пользователя в чате. Сервер повторно канонизирует путь внутри `wwwroot/uploads`, выставляет `nosniff`, безопасные raster-форматы допускает к inline-выдаче, остальные типы принудительно скачиваются. Web-клиент больше не использует прямые `/uploads/... ` URL: он получает файл через `fetchWithAuth` и использует временный Blob URL для изображения либо скачивания.


### 8. Авторизация и атомарность на границе MessageService/ChatService

Исправлено в текущей ветке. Мутационные операции сервисов теперь принимают actorId и повторно проверяют права внутри сервисного слоя. MessageService проверяет членство и авторство при удалении/редактировании, а массовое удаление выполняется атомарно: если хотя бы одно указанное сообщение отсутствует в заданном чате или принадлежит другому пользователю, изменение БД не выполняется.

ChatService проверяет роль вызывающего пользователя при добавлении/удалении участников, переименовании и удалении чата. Через сервис нельзя назначить привилегированную роль; удаление владельца/администратора и самоустранение через административную операцию запрещены. Удаление чата требует одновременно роли владельца и совпадения actorId с владельцем чата.

Проверка прав и изменение БД выполняются в одной PostgreSQL-транзакции для изменяемых операций, что закрывает основное TOCTOU-окно между отдельной проверкой контроллера и записью.

Инвалидация Redis после успешного commit стала best-effort для изменяемых операций: отказ Redis не превращает уже сохранённое изменение PostgreSQL в HTTP 500. Ошибка кеша логируется.

Оставшийся подэтап: перевести защищённые read-операции (получение сообщений, поиск, экспорт и pinned) на явный actorId в Application-контрактах, чтобы сервисный слой самостоятельно защищал и чтение, а не только мутации.


### 9. Защита read-операций MessageService/ChatService

Для HTTP read-операций добавлены actorId-overloads в сервисные контракты и реализации. Получение истории, поиск, экспорт и pinned-сообщения теперь могут выполняться через защищённые методы, которые сами проверяют членство пользователя. Аналогично получение конкретного чата и списка участников проверяет членство внутри ChatService.

MessagesController и ChatsController передают текущий userId в защищённые overloads. Поэтому доступ к чужому ChatId не зависит только от предварительной проверки контроллера и не может быть получен через этот Application-контракт без прохождения проверки членства.

Старые overloads без actorId сохранены для доверенных внутренних сценариев (consumer/background/service-to-service), где пользовательский authorization boundary отсутствует. HTTP endpoints используют только actor-aware overloads.


### 10. Модерация, Redis и rate limiter

Усилена граница модерации: жалобу на сообщение теперь можно создать только участнику соответствующего чата; причина жалобы обязательна. Обработка жалобы ограничивает допустимые статусы и переводит только pending-репорты, чтобы конкурентный повторный review не перезаписывал уже обработанную запись.

Проверка системной роли администратора теперь выполняется не только в контроллерах, но и внутри ModerationService для выдачи/снятия mute, чтения pending reports, moderation logs и active mutes, review/delete report и удаления moderation log. Для этого actorId обязателен в Application-контрактах административных операций; контроллеры передают разрешённый id, а сервис повторно проверяет его через IAdminService. Это закрывает обход HTTP-контроллера при прямом вызове Application-сервиса.

Лимиты административных выборок модерации ограничены диапазоном 1..200 для pending reports и 1..500 для moderation logs. Добавлен PostgreSQL integration test, проверяющий отказ MuteUserAsync для пользователя без системной роли администратора.

RedisCacheService связывает ожидание Redis-команд с CancellationToken через WaitAsync, поэтому отменённая HTTP/background operation не зависает до завершения Redis-команды. Ошибки Redis по-прежнему деградируют в cache miss/no-op, а отмена пробрасывается.

Realtime rate limiter теперь принимает CancellationToken. HTTP отправка сообщений и SignalR typing/send-permit передают отмену запроса/соединения вместо ожидания queued permit после disconnect/cancel.


### 11. Остановка фоновых служб и cancellation

Проверены `PresenceHeartbeatBackgroundService`, `SessionCleanupBackgroundService`, `ScheduledMessageDispatcherService`, `UploadOrphanCleanupService`, `RedisMetricsCollectorService`, `LogRetentionService` и `TokenRefreshBackgroundService`.

Во всех циклах отмена отделена от обычной ошибки и не должна превращаться в retry/error log. Для `SessionCleanupBackgroundService` и `RedisMetricsCollectorService` дополнительно обработана отмена стартовой задержки до первого рабочего тика: shutdown в этот момент теперь завершается штатно через `return`, без выхода из `ExecuteAsync` по необработанному `OperationCanceledException`.

`ScheduledMessageDispatcherService` и `UploadOrphanCleanupService` уже имели корректную обработку startup-delay. `PresenceHeartbeatBackgroundService` выполняет startup delay непосредственно внутри `try/catch` с фильтром shutdown cancellation. `LogRetentionService` использует `PeriodicTimer` и отдельную обработку отмены. `TokenRefreshBackgroundService` также фильтрует shutdown cancellation на уровне timer loop и отдельных операций.

Обычные ошибки фоновых операций остаются recoverable: текущий тик логирует ошибку и цикл продолжает работу. Для файловой уборки уже предусмотрена более длинная задержка после ошибки (`10 минут` вместо штатных `6 часов`). Остальные службы используют штатный фиксированный интервал; отдельный глобальный exponential backoff не вводился, поскольку для cleanup/metrics/heartbeat фиксированные интервалы предсказуемее и уже ограничивают частоту повторов.

Отдельно подтверждено, что consumer `ChatMessageSentConsumer` не подавляет `OperationCanceledException`: отмена передаётся MassTransit, а transient-ошибки push пробрасываются для broker retry.


### 12. Application-контракты и получение текущего пользователя

Проверены интерфейсы `IAccountSettingsService`, `IAdminService`, `IAttachmentService`, `IBroadcastRepository`, `IBroadcastService`, `ICacheService`, `IChatFolderService`, `IChatService`, `IEncryptionService`, `ILoginService`, `IMessageService`, `IModerationService`, `INotificationService`, `IPushSubscriptionService`, `IReactionService`, `IScheduledMessageService`, `IUserPresenceTracker`, `IUserService` и `IUserStatusService`. Асинхронные операции Application-сервисов в этих контрактах принимают `CancellationToken` (с optional default); синхронные/чистые операции и функции шифрования не требуют искусственного токена.

Найден пропуск в API boundary: `ClaimsPrincipalExtension.GetCurrentUserAsync` и `GetCurrentUserIdAsync` не принимали токен, из-за чего загрузка пользователя по externalId выполнялась без отмены даже в HTTP-запросе. Методы расширения теперь принимают `CancellationToken` и передают его в `IUserService.GetUserByExternalIdAsync`. Все вызовы этих helpers в API-контроллерах передают request `ct`. Дополнительно исправлен прямой вызов `UsersController.GetUserByExternalIdAsync`, который ранее игнорировал свой параметр `ct`.

Это устраняет потерю отмены на общем пути разрешения текущего пользователя. Полный аудит всех вызовов Application-методов из каждого background/internal компонента и автоматизированная проверка отсутствующих аргументов токена остаются частью проверки сборкой/тестами; наличие параметра в интерфейсе само по себе не доказывает, что каждый caller его передаёт.

### 13. Отмена HTTP-запросов в API-контроллерах

В API-контроллерах общий `catch (Exception)` больше не должен превращать отмену клиентского HTTP-запроса в ответ 500. Перед общими обработчиками добавлен отдельный `catch (OperationCanceledException) when (ct.IsCancellationRequested)`, который повторно выбрасывает исключение и позволяет ASP.NET Core завершить отменённый запрос штатно.

Проверены и обновлены контроллеры AccountSettings, Admin, Attachments, Authorization, Broadcasts, ChatFolders, Chats, Logins, Messages, Moderation, Notifications, OAuthProxy, Push, Reactions, ScheduledMessages, UserStatuses и Users. Вложенные best-effort SignalR-отправки в ScheduledMessagesController и MessagesController также не подавляют отмену самого HTTP-запроса. Отфильтрованные обработчики локальной очистки файлов, не относящиеся к HTTP-операциям, не менялись.

Фильтр по `ct.IsCancellationRequested` намеренный: отмена внутренней операции по таймауту, не вызванная отменой входящего HTTP-запроса, остаётся обычной ошибкой и проходит в существующую обработку. Проверка не заменяет интеграционные тесты на disconnect/cancel во время DB, Redis, HTTP и файловых операций.

### 14. Передача CancellationToken во внутренних компонентах

Продолжена проверка не только наличия токена в Application-контрактах, но и фактической передачи из consumers, background services и SignalR.

Подтверждено:
- `ChatMessageSentConsumer` передаёт `ConsumeContext.CancellationToken` в операции сообщений, вложений, статусов доставки, push и SignalR; отмена consumer не подавляется.
- `ScheduledMessageDispatcherService` передаёт stopping token в dispatch, загрузку отправителя, публикацию в MassTransit Outbox и SignalR.
- `SessionCleanupBackgroundService` передаёт stopping token в distributed lock, статусы, Presence checks, закрытие login-сессий и SignalR.
- `PresenceHeartbeatBackgroundService` передаёт stopping token в heartbeat.
- `UploadOrphanCleanupService` передаёт токен в EF-запросы и ADO.NET open/read.
- `LogRetentionService` передаёт токен в SQL delete и задержки; отмена не превращается в обычную ошибку cleanup.
- `RedisMetricsCollectorService`: Redis `PingAsync` и `InfoAsync` не имеют CancellationToken overload, поэтому ожидание теперь ограничено через `WaitAsync(ct)`.
- `RedisDistributedLock`: ожидание `StringSetAsync` ограничено через `WaitAsync(ct)`. Если отмена приходит во время уже отправленной Redis-команды, фоновая компенсация дожидается результата и освобождает lock только при совпадении owner token; при сбое ключ ограничен TTL.
- `RedisUserPresenceTracker`: Redis Lua-команды connect/disconnect/has-connections/heartbeat теперь ожидаются через `WaitAsync(cancellationToken)`. Для отменённого connect добавлена компенсация: после завершения исходной команды удаляется только соответствующий connectionId, чтобы поздно завершившийся Redis write не оставил лишний Presence lease.

В `ChatHub` исправлены пропуски передачи `Context.ConnectionAborted`: получение пользователя, настройки, статусы, Presence connect, rate limiter, SignalR group membership и отправки событий теперь учитывают жизненный цикл соединения. Best-effort чтение настроек отдельно пробрасывает отмену, а не скрывает её общим пустым catch.

Важное исключение: `OnDisconnectedAsync` намеренно не использует `Context.ConnectionAborted` для Presence cleanup и перевода статуса Offline. При вызове callback токен соединения уже может быть отменён; его передача прервала бы обязательную очистку после disconnect. Для этих операций сохранено выполнение без connection token. Это сознательное разделение пользовательской работы и cleanup после разрыва соединения.

Аудит охватил перечисленные основные consumers/background/realtime-компоненты. Это не является доказательством отсутствия пропусков во всех произвольных внутренних вызовах решения; необходимы сборка, анализаторы и тесты отмены.

### 15. Рефакторинг точки композиции Messenger.API

`Messenger.API/Program.cs` сокращён до последовательности запуска приложения. Конфигурация разделена на тематические extension-классы:
- `ApiServiceCollectionExtensions`: логирование, JSON, DI, фоновые службы, безопасность, CORS и OpenTelemetry;
- `ApiApplicationBuilderExtensions`: применение миграций, настройка middleware, обработка SignalR access token и публикация endpoint'ов.

Порядок регистрации зависимостей сохранён: API logging и shared development encryption key выполняются до остальных регистраций; hosted services, authentication/rate limiting, session/log cleanup, health checks и Redis metrics регистрируются в прежней последовательности.

Порядок запуска сохранён: миграции выполняются до обработки запросов; сначала подключаются request logging и SignalR query-token middleware, затем отображаются Scalar/health/metrics endpoint'ы; после этого подключаются static assets, CORS, HTTPS, authentication/authorization, development Serilog UI и rate limiter; в конце публикуются controllers и SignalR hubs. Маршруты, CORS policy, API version fallback и настройки сериализации перенесены без изменения значений.

Это структурный рефакторинг точки композиции, а не перенос бизнес-логики или изменение поведения endpoints. Обязательная проверка сборкой и smoke/integration tests ещё не выполнена.
